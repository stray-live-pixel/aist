# Flows

Каждый flow — это папка `flows/<name>/` с метаданными и набором этапов.
Запуск: `./agent-auto.sh [--engine claude|codex] --flow <name> [--html|--ui] [extra prompt]`.

## Структура

```
flows/<name>/
├── .index.md         ← метаданные flow + явный список этапов
├── implement.md      ← stage-файл (имя любое)
├── review.md
└── tests.md
```

Файл метаданных называется `.index.md` (с точкой), чтобы не сливаться со стейджами в файловом дереве. Имена stage-файлов произвольные — порядок определяет `stages:` в `.index.md`.

## .index.md

```markdown
---
title: My Flow
description: Краткое описание.
model: claude-opus-4-7 # дефолт для всех этапов; можно опустить
codex_model: gpt-5.5 # дефолт для Codex; опционально
default_summary_rules: |
  Перечисли изменённые файлы и ключевые решения.
  Только факты, без воды.
stages:
  - implement.md
  - review.md
  - tests.md
---

# Опциональный человеческий текст

Любая дополнительная информация для разработчиков flow.
```

## stage-файл

Контекст стейджа описывается списком `contexts:` — каждая запись задаёт один
источник контекста. Если поля нет (или список пуст) — стейдж работает как
standalone: свежая сессия без `--resume` и без преамбул.

```markdown
---
title: Code review # для UI; по умолчанию — имя файла
model: claude-haiku-4-5-20251001 # переопределяет дефолт из .index.md
codex_model: gpt-5.4-mini # переопределяет Codex-модель точечно
summary_rules: | # дефолт для summary-from в этом стейдже
  Только список путей и решений.
contexts:
  - mode: continue-from
    from: 1
---

# Промпт этапа

Markdown, который будет передан выбранному агенту.
```

## Модели

- `model:` в `.index.md` — дефолт для всех этапов flow.
- `model:` во frontmatter этапа — переопределяет дефолт точечно.
- Если не указано нигде — для Claude используется `claude-opus-4-7`.

Для Claude значение передаётся в `claude --model <id>`. В `summary-from`
суммаризационный прогон и основной запуск используют одну и ту же модель этапа.

Для `--engine codex` предпочтительно использовать `codex_model:` в `.index.md`
или stage-файлах. Если `codex_model:` не указан, а `model:` не начинается с
`claude-`, это значение используется как Codex-модель. Если и такого значения
нет, Codex CLI берёт модель из своей конфигурации или `AGENT_AUTO_CODEX_MODEL`.
В UI это отображается как `codex-default`.

## Контексты (`contexts:`)

Каждая запись — мини-конфиг одного источника контекста:

| mode            | Поведение                                                                                                                      |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `continue`      | `--resume <session этапа from>`. Контекст растёт линейно. Поле `from:` можно опустить — тогда возьмётся `idx - 1`.             |
| `continue-from` | Форк сессии этапа `from` (`cp` jsonl под новым uuid) и `--resume` форка. Исходник не меняется, можно использовать многократно. |
| `summary-from`  | Суммаризационный прогон по форку источника по `summary_rules` → текст summary вшивается в начало промпта основного запуска.    |

```markdown
---
title: Реализация
contexts:
  - mode: continue-from # форк сессии этапа 1 — основной контекст
    from: 1
  - mode: summary-from # + краткое summary этапа 3 как преамбула
    from: 3
    summary_rules: | # опционально, иначе наследуется
      Только список изменённых файлов и принятые решения.
---
```

Правила:

- порядок записей сохраняется: summary-преамбулы вставляются в промпт в том же
  порядке, что и в `contexts:`;
- максимум один resume-контекст (`continue` / `continue-from`) на этап — нельзя
  одновременно ресюмить две сессии;
- `summary-from` можно добавлять сколько угодно — каждый прогон делается на
  отдельном форке источника, исходные сессии не меняются;
- `from:` — 1-based номер этапа в `stages:`, обязан быть меньше текущего;
- `summary_rules` каскадирует: per-context → stage-level (`summary_rules:`) →
  flow-level (`default_summary_rules:` в `.index.md`).

Финальный промпт собирается так:

```
## Контекст из этапа K (summary)
<summary_K>
---
## Контекст из этапа L (summary)
<summary_L>
---
<EXTRA_PROMPT из CLI, если есть>
---
<тело stage.md>
```

В UI бейдж этапа отображает компактную сводку контекстов:

- `standalone` — пустой/отсутствующий список;
- `continue-from(1)` — один контекст;
- `continue-from(1)+summary-from(3)` — несколько.

Если форк не удался (`~/.claude/projects/<...>/<id>.jsonl` для Claude или
`~/.codex/sessions/.../rollout-...<id>.jsonl` для Codex не существует или нет
прав на копирование), flow явно останавливается с записью ошибки в общий лог и
`<session>/flow.json`.

## Извне передаваемый prompt

`./agent-auto.sh --flow X "Дополнительный контекст"` — текст после `--flow X` приклеивается к **каждому** этапу как преамбула. Полезно для глобальных уточнений.

## State-файлы сессии

В `.agent-auto-logs/<session>/flows/` хранятся:

- `stage-NN.info.json` — `sessionId`, `result`, токены этапа (пишет парсер).
- `stage-NN.session.jsonl` — снимок jsonl-сессии после завершения этапа (на случай, если потребуется ручной разбор).
- `stage-NN.fifo` — временный FIFO между агентом и парсером (удаляется после этапа).
- `stage-NN.stderr.log` — stderr Codex CLI, если flow запущен с `--engine codex`.

Текущее состояние flow — `<session>/flow.json`. UI его опрашивает и рисует pipeline.

## Dry run

Для отладки оркестратора без реального агента:

```
./agent-auto.sh --flow <name> --html --dry-run
```

Каждый этап эмулируется synthetic-событиями выбранного backend-а — UI и логи получают данные, можно проверить визуализацию.
