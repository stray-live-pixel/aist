# Логика автономных агентов в Docker-контейнере

Session: `8ce4e3bb-d960-4707-a4b6-b9e2f2b302ac`

## Коротко

Изолированный автономный агент в AIST — это отдельный запуск обычного agent runtime, но не в основном рабочем дереве проекта, а в отдельном git worktree и с bash-командами внутри Docker-контейнера.

Главная идея продукта: пользователь запускает задачу из UI, AIST сам создаёт отдельную ветку, даёт агенту безопасную копию проекта, запускает контейнер для команд, а после работы сам делает commit/push/PR. VS Code при этом остаётся только интерфейсом, а source of truth — daemon.

## Простая схема

```text
Пользователь в VS Code Webview
  ↓ isolation.start
Extension host / bridge
  ↓ JSON-RPC
AIST CLI daemon
  ↓
IsolationSessionManager
  ├─ создаёт session и пишет durable state/logs
  ├─ создаёт git worktree и ветку
  ├─ запускает Docker container
  ├─ запускает отдельный AgentRuntimeService
  │    ├─ model requests идут из daemon наружу к модели
  │    ├─ file tools работают по isolated worktree
  │    └─ run_bash_script выполняется через docker exec
  └─ после агента:
       ├─ удаляет контейнер
       ├─ делает git commit
       ├─ push в remote, если remote есть
       └─ создаёт или читает PR через gh, если возможно
```

## Какие слои где запускаются

### 1. Webview — только пользовательский экран

Файлы: `src/webview/pages/isolation/IsolationPage.tsx`, `src/webview/shared/lib/agentActions.ts`.

Webview показывает список изолированных сессий, статусы, кнопки запуска/остановки/открытия worktree/PR. Сам агент здесь не работает.

### 2. Extension host — тонкий адаптер VS Code

Файлы: `src/extension/agent/agentController/webviewMessageActions.ts`, `src/extension/agent/daemon/bridge/isolationBridgeActions.ts`.

Extension принимает действие `isolation.start` из webview и отправляет daemon JSON-RPC запрос `isolation.start`. Также обновляет UI-состояние, открывает папку worktree или PR-ссылку. Агентскую логику extension не содержит.

### 3. CLI daemon — главный backend и source of truth

Файлы: `src/cli/daemonServer/AistDaemonServer.ts`, `src/cli/daemonServer/isolation/IsolationSessionManager.ts`.

Daemon держит `IsolationSessionManager`. Именно daemon создаёт сессию, хранит состояние, запускает Docker, запускает runtime, пишет логи и финализирует git-результат.

Состояние хранится не в workspace, а в user-personal storage:

```text
~/.aist-agent/workspaces/<workspace-key>/isolation/
  sessions.json
  events/<session-id>.jsonl
  worktrees/<session-id>/
```

Поэтому UI может закрыться и открыться снова: daemon/extension перечитает состояние из storage.

### 4. Git layer — отдельная ветка и worktree

Файл: `src/cli/daemonServer/isolation/git/IsolationGitService.ts`.

При старте создаётся:

- `taskId` — случайный id;
- `sessionId` — случайный id;
- ветка вида `aist/task/<первые-12-символов-taskId>`;
- worktree по пути `~/.aist-agent/workspaces/<workspace-key>/isolation/worktrees/<sessionId>`.

Алгоритм:

1. daemon находит root git-репозитория через `git rev-parse --show-toplevel`;
2. выбирает remote: сначала `origin`, иначе первый доступный remote;
3. если пользователь передал `baseRef`, берёт его, иначе для первого запуска берёт `HEAD`;
4. если это continue/retry и ветка уже есть — использует текущую ветку;
5. создаёт worktree:
   - если локальная ветка уже есть: `git worktree add <worktreePath> <branchName>`;
   - если ветки нет: `git worktree add -B <branchName> <worktreePath> <baseRef>`.

Важно: оригинальный workspace не модифицируется. Все изменения агента должны попадать в isolated worktree.

### 5. Docker layer — контейнер для bash-команд

Файл: `src/cli/daemonServer/isolation/LocalDockerIsolationProvider.ts`.

Перед запуском daemon проверяет Docker:

```bash
docker version --format '{{.Server.Version}}'
```

Контейнер стартует командой по смыслу такой:

```bash
docker run -d \
  --name aist-isolated-<sessionId> \
  --label aist.isolated=true \
  --label aist.sessionId=<sessionId> \
  -v <worktreePath>:/workspace \
  -w /workspace \
  node:20-bookworm \
  sleep 86400
```

Текущий образ по умолчанию: `node:20-bookworm`.

Контейнер не запускает агента как отдельный Node-процесс. Он просто живёт как sandbox для shell-команд. Агентский runtime остаётся в daemon-процессе на хосте, а когда модель вызывает `run_bash_script`, daemon делает:

```bash
docker exec -w /workspace[/cwd] <container> bash -lc '<script>'
```

Рабочая директория внутри контейнера всегда нормализуется к `/workspace` или подпапке `/workspace`. Попытки уйти через `..` сбрасываются к `/workspace`.

### 6. Agent runtime — тот же core runtime, но с isolated adapters

Файл: `src/cli/daemonServer/methods/runIsolationAgent.ts`.

Daemon создаёт отдельный `AgentRuntimeService` для isolated session:

- chat id: `isolation-<sessionId>`;
- chat repository: in-memory, чтобы не смешивать isolated run с обычным чатом;
- run repository: общий daemon run repository, чтобы run можно было логировать;
- model client: тот же routing model client, что и у обычного агента;
- prompt: обычный file-based system prompt + специальные isolated-инструкции.

Специальные инструкции говорят агенту:

- работать только в isolated worktree;
- bash-команды выполняются в Docker с `/workspace`;
- не трогать оригинальный workspace;
- не делать commit/push/PR вручную;
- всегда создать или обновить `docs/aist-isolated-runs/<sessionId>.md`;
- если задача аналитическая, полный ответ записать в этот markdown artifact;
- если были изменения кода, записать summary и verification notes;
- run считается неполным, пока не изменён хотя бы один файл.

## Как работают инструменты внутри isolated run

Файл: `src/cli/daemonServer/isolation/runtime/createIsolatedToolCallHandler.ts`.

Для isolated session включён специальный tool handler:

```text
Tool call от модели
  ↓
ToolRunner
  ├─ run_bash_script → docker exec внутри container
  ├─ read/write/list/grep/etc → Node filesystem runner по worktreePath
  ├─ project tools → запускаются с workspaceRoot = worktreePath
  ├─ custom skills → запускаются с workspaceRoot = worktreePath
  └─ auxiliary model tools → через daemon auxiliaryModel
```

Особенность approvals: для isolated runtime approval service всегда возвращает `auto approve`. То есть внутри изолированного агента нет пользовательских подтверждений на каждый tool call. Безопасность обеспечивается тем, что агент работает в отдельном worktree и bash уходит в Docker-контейнер.

## Устанавливаются ли зависимости автоматически

Сейчас отдельного шага `npm install`, `npm ci`, `pnpm install` или `yarn install` в lifecycle isolated session нет.

Что реально происходит:

1. создаётся git worktree;
2. запускается контейнер `node:20-bookworm`;
3. worktree монтируется в контейнер как `/workspace`;
4. агент сам решает, какие команды запускать.

Если в проекте уже есть `node_modules` в git worktree — они будут доступны только если реально присутствуют в этом worktree. Обычно `node_modules` не коммитится, значит внутри isolated worktree зависимостей не будет, пока агент сам не выполнит `npm install`/`npm ci`/другую команду.

Практический вывод: установка зависимостей — не автоматический системный шаг, а действие агента через `run_bash_script`, если он сочтёт это нужным для задачи или проверки.

## Что есть в Docker-образе

Используется официальный образ `node:20-bookworm`.

Продуктово это означает:

- есть Node.js 20;
- есть Debian Bookworm окружение;
- есть bash;
- обычно есть npm вместе с Node-образом;
- проектные зависимости не предустановлены;
- дополнительные системные пакеты не устанавливаются автоматически.

Если агенту нужен другой toolchain, он должен поставить его командой внутри контейнера, если это возможно.

## Финализация результата

После того как runtime завершился успешно:

1. daemon переводит сессию в `post_processing`;
2. удаляет Docker container через `docker rm -f`;
3. проверяет изменения в worktree через `git status --porcelain`;
4. если изменений нет, пытается создать fallback artifact `docs/aist-isolated-runs/<sessionId>.md` с ответом агента;
5. если изменения есть:
   - делает `git add -A`;
   - делает `git commit -m <короткий prompt>`, с `AIST isolated session: <sessionId>` во второй строке;
   - если remote есть, делает `git push -u <remoteName> <branchName>`;
   - если доступен `gh`, пытается найти существующий PR или создать новый через `gh pr create --fill --head <branchName>`;
6. сессия становится `ready_for_review`.

Если remote не настроен — PR не создаётся, daemon пишет warning в лог.

Если `gh` недоступен или PR не создался — commit/push могут быть готовы, а ошибка PR сохраняется в `prError`.

## Статусы сессии простыми словами

```text
queued          задача принята
creating        создаётся запись/начинается provisioning
preparing       готовится git worktree
running_agent   агент работает с моделью и tools
post_processing агент закончил, daemon собирает результат
committing      daemon создаёт commit
pushing         daemon пушит ветку
creating_pr     daemon создаёт или читает PR
ready_for_review результат готов к ревью
failed          ошибка
stopping        пользователь остановил сессию
 destroyed      контейнер/worktree уничтожены или сессия закрыта
```

## Что происходит при stop/destroy/continue

### Stop

`isolation.stop`:

- переводит сессию в `stopping`;
- вызывает `runtime.stop()`;
- удаляет контейнер;
- выставляет статус `destroyed`;
- worktree при stop не удаляется в текущей реализации.

### Destroy

`isolation.destroy`:

- останавливает runtime;
- удаляет контейнер;
- удаляет git worktree;
- выставляет статус `destroyed`;
- публикует событие `isolation.session.destroyed`.

### Continue

`isolation.continue`:

- берёт существующую сессию;
- заменяет prompt;
- увеличивает attempt;
- снова запускает provisioning;
- для baseRef использует существующую ветку, если это продолжение.

## Важные ограничения текущей реализации

- Docker должен быть установлен и запущен локально.
- Используется только provider `docker-local`.
- Образ сейчас захардкожен по умолчанию как `node:20-bookworm`, если не передать другой image в provider options; пользовательской настройки image в публичном flow не видно.
- Зависимости проекта не устанавливаются автоматически.
- Контейнер используется для bash-команд, но модельный runtime работает в daemon на хосте.
- Файловые операции read/write идут Node filesystem runner-ом по isolated worktree на хосте, не через Docker.
- Commit/push/PR делает daemon на хосте, не контейнер.
- PR требует настроенный remote и установленный/авторизованный `gh` CLI.
- Если daemon перезапустился во время активной сессии, активные статусы восстанавливаются как `failed` с текстом: `Daemon restarted while this isolated session was active. Use Retry/Continue from UI.`

## Итоговая продуктовая формулировка

AIST isolated agent — это «агент на отдельной ветке»: daemon создаёт отдельный git worktree, поднимает рядом Docker-контейнер с `node:20-bookworm`, запускает обычный AIST runtime с особыми правилами, выполняет shell-команды через контейнер, пишет файлы только в worktree, а затем сам упаковывает результат в commit/branch/PR. Автоматической установки зависимостей нет: агент должен сам запустить нужную install-команду, если проверки или разработка этого требуют.
