# apply_patch

`apply_patch` сейчас намеренно не реализован как исполняемый инструмент.

Эта папка оставлена как архитектурная заготовка для будущей утилиты работы с patch-изменениями в домене `fs`.

## Идея инструмента

Будущий `apply_patch` должен применять структурированный patch к файлам workspace безопаснее, чем ручной запуск shell-команд или полная перезапись файлов.

Основной сценарий:

1. Агент передаёт patch в понятном формате.
2. Утилита валидирует все затрагиваемые пути.
3. Утилита строит предварительный план изменений по каждому файлу.
4. Пользователь видит preview/diff до применения изменений.
5. После подтверждения утилита применяет изменения атомарно насколько это возможно.
6. Результат возвращает краткую сводку: изменённые файлы, созданные файлы, диапазоны изменённых строк и диагностические предупреждения.

## Продуктовые требования

- Инструмент работает только внутри workspace.
- Абсолютные пути, `..`, symlink escape и binary patches запрещены.
- Удаление файлов должно быть явным отдельным действием, а не побочным эффектом patch.
- Multi-file patch должен показывать preview по каждому файлу.
- При ошибке применения ни один уже изменённый файл не должен остаться в частично изменённом состоянии.
- Для больших изменений инструмент должен возвращать компактный model-result и полный UI-result.
- Ошибки должны быть структурированными и помогать агенту восстановиться: `INVALID_ARGUMENT`, `PATH_OUTSIDE_WORKSPACE`, `TEXT_NOT_FOUND`, `PATCH_CONFLICT`.

## Архитектурные правила будущей реализации

- Один инструмент — одна папка: `src/core/tools/fs/apply_patch`.
- Общие утилиты уровня всех инструментов должны лежать в `src/core/tools/shared`.
- Общие filesystem-утилиты должны лежать в `src/core/tools/fs/shared`.
- Каждая функция или утилита должна быть в отдельном файле, если начинает переиспользоваться или усложняется.
- Все функции принимают аргументы объектом: `runApplyPatchTool({ context, args })`.
- Комментарии в коде должны объяснять продуктовый смысл шагов на русском языке.
- Unit-тесты должны покрывать happy path, конфликт patch, rollback, защиту workspace и preview-контракт.

## Почему старая реализация удалена

Старая реализация была legacy-кодом вне новой структуры инструментов и смешивала несколько ответственностей: парсинг unified diff, применение файлов, rollback, preview и runtime-регистрацию.

Перед повторным включением `apply_patch` нужно спроектировать новый контракт инструмента и реализовать его в этой папке без переноса старого кода как есть.
