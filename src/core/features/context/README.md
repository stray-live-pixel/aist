# Context Governor

Этот раздел фиксирует старую механику управления контекстом агента, которая была отключена и признана плохим решением.
Документ нужен как историческая справка: если позже мы вернемся к оптимизации контекста, важно не повторить прежнюю ошибку.

## Почему старая стратегия была плохим решением

Старый `contextGovernor` пытался экономить контекст модели через агрессивное урезание истории чата и замену части данных короткими summary. Для coding-agent сценариев это оказалось вредным.

Главная проблема: история чата для агента — это не просто лог переписки, а рабочая память текущей задачи. В начале диалога часто находятся ключевые требования, ограничения, архитектурные договоренности и уже найденный контекст. Когда governor оставлял только хвост истории, агент терял смысл предыдущей работы и почти на каждом новом prompt вынужден был заново собирать те же сведения через tools.

Что именно не работало:

- история резалась по возрасту и размеру, а не по продуктовому смыслу;
- ранние требования пользователя выпадали первыми, хотя часто были самыми важными;
- tool results сжимались слишком коротко и теряли детали диагностики;
- активный editor context добавлялся только при довольно узких условиях;
- repo hints, memory и editor context были связаны с общей агрессивной упаковкой;
- не было надежного running summary, который мог бы заменить удаленную историю;
- экономия токенов приводила к повторной работе агента и ухудшению UX.

## Вывод

Старый подход был слишком агрессивным: он оптимизировал размер prompt, но ухудшал непрерывность работы агента. Для будущих версий управления контекстом нельзя просто удалять историю по хвосту. Нужен более бережный подход: сохранять пользовательские требования и смысл задачи, явно отделять долговременную память от текущей истории и не заменять важные tool results слишком короткими summary.
